# lib-go

> A library of reusable code for my personal Golang projects.

## 🎯 Motivation

Golang is my primary language of choice when developing personal projects that requires a backend. 

There are some common patterns and code that I find myself repeating across all my projects, such as setting up logging, database migrations, various utilities to work with time, pointers, etc.

The purpose of this library is to have those common code in one place, so I can easily reuse it across all my projects. Having this library also forces me to think about creating reusable code and abstractions, which is a good practice in software development.

## 📋 What is included

### Utilities

- [`cache`](cache/README.md): Key-value cache abstraction with pluggable backends.
- [`env`](env/README.md): Typed environment variable helpers.
- [`errs`](errs/README.md): Structured, transport-agnostic application error type.
- [`events`](events/README.md): Synchronous, in-process event bus.
- [`nullable`](nullable/README.md): Generic nullable value type for database-friendly code.
- [`pagination`](pagination/README.md): Offset-based and cursor-based pagination types.
- [`ptr`](ptr/README.md): Generic pointer utilities.
- [`sorting`](sorting/README.md): Validated sort order types for repository queries.
- [`timeutil`](timeutil/README.md): Testable time abstractions (`Clock`, `Sleeper`, `Ticker`).
- [`uow`](uow/README.md): Unit of Work interfaces for cross-repository transactions.
- [`validator`](validator/README.md): Composable field validator.

### HTTP

- [`apidoc`](apidoc/README.md): HTTP handler for serving an OpenAPI spec and Scalar UI.
- [`httpapi`](httpapi/README.md): Helpers for building JSON HTTP APIs.
- [`httpserver`](httpserver/README.md): HTTP server with sane defaults and graceful shutdown.
- [`middleware`](middleware/README.md): Common HTTP middleware.
- [`spa`](spa/README.md): HTTP handler for serving single-page applications.

### Observability

- [`logging`](logging/README.md): Structured logger built on `log/slog`.
- [`mailer`](mailer/README.md): Email abstraction with pluggable backends.

### Testing

- [`openapitest`](openapitest/README.md): Validate HTTP requests and responses against an OpenAPI spec.

### Sub-modules

The following packages are distributed as separate Go modules to keep heavy dependencies opt-in:

| Module | Import path | Description |
|--------|-------------|-------------|
| `tracing` | `github.com/brpaz/lib-go/tracing` | OpenTelemetry tracing: `Provider` (OTLP/gRPC `TracerProvider`), `StartSpan`/`EndSpan` helpers, and HTTP/test helpers in `tracing/middleware` and `tracing/tracingtest`. |
| `db` | `github.com/brpaz/lib-go/db` | Driver-agnostic database connectivity helpers built on GORM, with `migrator` (goose schema migrations), `uow` (GORM-backed unit of work), `gormlog` (GORM logger adapters) and `dbtest` (Postgres testcontainers / SQLite test helpers). |

## 🚀 Getting started

### Installation

```shell
go get github.com/brpaz/lib-go
```

For sub-modules, install them separately:

```shell
go get github.com/brpaz/lib-go/tracing
go get github.com/brpaz/lib-go/db
```

### Usage

Each package includes a `README.md` file generated by [Gomarkdoc](https://github.com/princjef/gomarkdoc), with documentation and examples for that package.

## 🧑‍💻 Development Quick start

This project uses [Devenv](https://devenv.sh/getting-started/) as the development environment. Devenv provides an isolated development environment with all the necessary tools and dependencies, without polluting the host machine.

### Prerequisites

- [Devenv](https://devenv.sh/getting-started/) 
- [Direnv](https://direnv.net/)

### Quick start

- Clone the repository:

```shell
git clone https://github.com/brpaz/lib-go
cd lib-go
```

- Enter the development environment:

```shell
direnv allow
```

- Run tests:

```shell
task test
```

## 📦 Adding a new sub-module

Most packages belong in the root module (`github.com/brpaz/lib-go`). Create a separate Go module only when a package would force heavy dependencies on all consumers — for example, a full SDK, a gRPC stack, or a large framework.

### When to create a sub-module

- The package imports a dependency that is significantly heavier than what the rest of the library pulls in (e.g. gRPC, a database driver, a full observability SDK).
- Consumers of the package are a subset of the library's users and should be able to opt into the extra weight explicitly.
- The package is otherwise self-contained and does not need to import the root module.

### Steps

1. **Create the package directory** and add a `go.mod` with the sub-module path:

```shell
mkdir -p mypackage
cd mypackage
go mod init github.com/brpaz/lib-go/mypackage
```

2. **Add a `go.work` entry** so the workspace recognises the new module:

```shell
go work use ./mypackage
```

3. **Write the package** following the same conventions as the root module.

4. **Run `go mod tidy`** inside the sub-module directory to populate `go.sum`.

5. **Update this README** — add a row to the sub-modules table and an entry in the relevant section above.

6. **Add a release-drafter config** at `.github/release-drafter-<name>-config.yml` (copy an existing one and update `name-template` and `tag-template` to use the `mypackage/v$RESOLVED_VERSION` prefix).

7. **Update the release-drafter workflow** (`.github/workflows/release-drafter.yml`) to add a step for the new config.

The Taskfile and CI matrix pick up new modules automatically via `git ls-files`, so no changes are needed there.
